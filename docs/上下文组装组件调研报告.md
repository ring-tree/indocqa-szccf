# 上下文组装组件技术调研报告

> 调研对象：GitHub 星标不低于 1000 的检索增强生成（RAG）、Agent 记忆与会话上下文管理开源项目  
> 调研时间：2026 年 11 月  
> 关联任务：工阅 IndocQA 会话上下文组装组件技术优化专项  
> 结论用途：为《上下文组装组件设计方案》提供路线选择与工程依据

---

## 摘要

大模型的长时记忆能力并不取决于“把更多文本塞进窗口”，而取决于在有限 token 预算内，**放入哪些信息、以什么顺序放入、如何证明信息来自哪里**。本报告调研了 12 个主流开源项目，将其归纳为四条技术路线：检索侧上下文工程、结构化记忆层、会话平台内置上下文窗口、Agent 状态编排与上下文压缩。四条路线分别解决“相关性”“长期性”“工程可用性”“状态一致性”问题，但没有任何单一项目同时满足本项目对语义去重、噪声过滤、严格 token 预算、全链路溯源、约束模板注入、画像与任务状态融合的要求。

结合 IndocQA 的单租户、离线可运行、中文工业文档、FastAPI + LangGraph + SQLite 技术栈，本报告建议采用**以检索侧上下文工程为骨架，融合轻量结构化记忆与会话级任务状态，自研统一组装层**的路线：不引入 Zep/Graphiti 一类多租户时序图谱，不在热路径增加记忆抽取 LLM 调用，复用现有 Chroma 向量与 fastembed 能力，以确定性算法保证预算与注入的可验证性。

## 1 调研背景与问题定义

### 1.1 长上下文不等于有效上下文

Liu 等人在《Lost in the Middle》中给出一个稳定结论：当相关信息位于长上下文的首尾时模型表现最好，位于中部时性能显著下降，且该现象在宣称支持长窗口的模型上依然存在[1]。工程界随后用“context rot（上下文腐化）”概括这一现象：随着上下文增长，模型的有效召回与指令遵循能力会持续衰减，真正可用的有效窗口远小于标称窗口[2]。

这意味着上下文组装的目标不是“填满窗口”，而是：

1. **降冗余**：重复段落不仅浪费预算，还会放大某一来源的权重，造成回答偏置；
2. **降噪声**：页眉页脚、目录残片、OCR 乱码会稀释注意力；
3. **保价值**：在硬预算内优先保留与当前问题、当前任务、用户画像最相关的信息；
4. **可追溯**：每个上下文单元必须能回到原始文档位置，否则引用与审计无从谈起；
5. **可约束**：系统规则必须稳定、完整、无错位地进入提示词，不能被资料内容挤占或覆盖。

### 1.2 本项目现状与差距

当前 IndocQA 的上下文拼装集中在 `server/app/generation/answerer.py` 的 `build_context()` 与 `server/app/graph/pipeline.py` 的 `chat_stream()`：

- 资料块按检索顺序直接拼接，仅带 `[n] 文档名 · 章节 · 页码` 的粗粒度标注，没有单元级唯一 ID、时间戳、会话节点与内容哈希；
- 会话历史按 `session_history_turns * 2` 条消息截断（默认 6 轮），按条数而非 token 控制，长文档问答时可能瞬间挤爆预算；
- 没有语义去重、近重复检测与噪声过滤，同一段落的多切片、跨文档转载会重复进入上下文；
- 没有显式 token 预算，`LLMGateway` 也未设置 `max_tokens`，上下文长度完全依赖上游模型兜底；
- 约束规则以固定字符串拼接，缺少模板版本、规则清单与渲染后校验；
- 不存在用户画像与任务状态数据结构，多轮追问仅靠 `_context_query()` 把上一轮问题拼进检索 query，跨轮任务信息在生成阶段丢失；
- 现有 `profile` 字段是“模型供应商 profile”，与“用户画像”同名不同义，设计时必须显式区分，避免接口歧义。

这些差距正是本次专项要系统性解决的五项痛点。

### 1.3 调研范围与方法

调研以 GitHub 仓库为主，辅以官方文档、设计博客与论文。入选标准：GitHub 星标不低于 1000；在 RAG 上下文组装、会话记忆或 Agent 状态管理方面有可辨识的工程实现；有公开代码或公开设计说明。星标量级为约数，仅用于说明项目影响力，不作为技术评价依据。

## 2 开源项目全景

| 项目 | 星标量级 | 定位 | 与上下文组装相关的机制 | 可借鉴点 |
|---|---|---|---|---|
| RAGFlow | 5 万+ | 深度文档理解 RAG 引擎 | 父子切片、TreeRAG 层级摘要、混合检索、RAPTOR 分层摘要、图谱推理 | 先精确定位再向上展开；切片策略与检索策略联动 |
| Dify | 10 万+ | LLM 应用编排平台 | TokenBufferMemory 按 token 丢弃最旧消息、会话变量、节点级上下文 | 预算不足时“丢旧保新”；用变量承载稳定事实 |
| AnythingLLM | 5 万+ | 私有知识库工作台 | 工作区隔离、文档固定（pin）、向量片段注入 | 会话/工作区级隔离；固定资料优先于相似度召回 |
| Open WebUI | 10 万+ | 本地模型交互界面 | top-k、chunk size/overlap、全文档注入模式、引用展示 | 检索参数可配置；引用与回答同屏呈现 |
| LlamaIndex | 4 万+ | 数据框架 | SentenceWindowNodeParser、HierarchicalNodeParser、AutoMergingRetriever、压缩检索器 | 小切片检索、大窗口生成；子节点命中比例触发父节点合并 |
| LangChain | 10 万+ | LLM 应用框架 | ContextualCompressionRetriever、摘要缓冲记忆 | 检索后压缩；历史摘要与原始消息混合 |
| LangGraph | 2 万+ | 有状态 Agent 编排 | Checkpointer 线程级状态、子图上下文隔离 | 会话级状态持久化；节点只读取本节点需要的上下文 |
| Haystack | 2 万+ | 检索流水线框架 | DocumentJoiner、Ranker、DocumentCompressor | 组装前的去重/排序/裁剪作为独立管道节点 |
| Mem0 | 4 万+ | 长期记忆层 | 事实抽取、增量合并（ADD/UPDATE/DELETE/NOOP）、向量+图谱混合检索 | 记忆写入做“抽取—合并—失效”，而非堆原始对话 |
| Zep / Graphiti | 2 万+ | 时序知识图谱记忆 | 双时间轴事实、有效性窗口、冲突消解 | 事实带时间与有效期，旧事实可失效而非删除 |
| Letta（MemGPT） | 2 万+ | 有状态 Agent 运行时 | 核心记忆块（可编辑）+ 归档记忆 + 召回记忆 | 稳定信息常驻上下文，长尾信息按需检索 |
| Kotaemon | 1 万+ | 文档问答 UI 框架 | 引用优先的答案展示、GraphRAG 支持 | 引用粒度与可读性并重 |

以上项目的共同趋势是：**上下文管理正在从“检索后拼接”演化为“分层记忆 + 预算调度 + 可观测组装”**。RAGFlow 0.23 引入父子切片并在图片、表格切片中补充上下文文本[3]；RAGFlow 的 TreeRAG 用离线 LLM 构建层级目录摘要，实现“先精确定位、再展开阅读”[4]；Mem0 采用单遍抽取、多信号检索与实体链接，将单次检索上下文控制在 7000 token 以内[5]；Dify 的 TokenBufferMemory 在超出 `max_token_limit` 时循环丢弃最旧消息[6]，模型未声明上下文大小时默认按 2000 token 处理[28]。

## 3 四条主流技术路线

### 3.1 路线一：检索侧上下文工程

**代表项目**：RAGFlow、LlamaIndex、Haystack、LangChain。

**核心机制**：

1. **层级切片**。LlamaIndex 的 `HierarchicalNodeParser` 把文档切成多级节点，每个子节点持有父节点引用；`AutoMergingRetriever` 在检索到的子节点占同一父节点比例超过阈值（默认 0.5）时，用父节点替换子节点，从而“用小切片保证检索精度，用大切片保证生成完整性”[7]。
2. **句子窗口**。`SentenceWindowNodeParser` 以单句为检索单元，但把前后各若干句存入元数据，生成前再扩展为窗口，兼顾精确命中与上下文连贯[8]。
3. **检索后压缩**。LangChain 的上下文压缩检索器、Haystack 的 `DocumentCompressor` 在召回后做相关性裁剪、摘要或去重，减少无关内容进入提示词。
4. **结构化展开**。RAGFlow 的父子切片与 TreeRAG 先定位到细粒度切片，再按文档树向上展开章节，避免“命中一句、丢失整节”的碎片化。

**优势**：

- 不依赖额外存储与写入链路，改造成本最低；
- 与现有向量库、BM25、重排器天然兼容；
- 对“答案在文档某一段”的工业问答收益直接、可量化。

**局限**：

- 多数实现只解决“相关性与完整性”，不解决跨轮记忆、用户画像与任务状态；
- token 预算常以条数或粗略字符数控制，缺少严格上限保证；
- 溯源多停留在 chunk 级，页面、表格行、上下文单元级别的审计能力不足；
- 去重多为完全重复或向量阈值，缺少“近重复 + 语义重复 + 互补性保留”的分级策略。

**适用场景**：文档问答、制度检索、手册查询等以“单轮事实获取”为主的系统。IndocQA 当前正处在这一路线的前半段，已有混合检索、重排、多跳与引用角标，但缺少组装层的预算、去重与溯源。

### 3.2 路线二：结构化记忆层

**代表项目**：Mem0、Zep/Graphiti、Letta。

**核心机制**：

1. **抽取式记忆**。Mem0 不把原始对话作为存储单元，而是抽取事实，再与已有记忆做增删改合并；其论文将流程概括为“抽取—整合—检索”，并在 LOCOMO 基准上系统比较了多种记忆增强方案[9]。工程博客进一步说明其采用单遍 ADD-only 抽取、多信号检索与实体链接，将检索上下文压到 7000 token 以内[5]。
2. **时序知识图谱**。Zep 的 Graphiti 以双时间轴记录事实的发生时间与写入时间，用有效期窗口处理“旧事实失效、新事实生效”，适合客户状态、工单状态频繁变化的场景[10]。
3. **分层记忆**。Letta（原 MemGPT）把上下文分为核心记忆块、归档记忆与召回记忆：稳定的人设与任务约束常驻核心块，长尾信息放入归档，需要时再检索[11]。

**优势**：

- 真正解决跨会话长期记忆与事实冲突；
- 记忆以事实为单位，token 效率高；
- 分层结构让“稳定约束”和“可变事实”各得其所。

**局限**：

- 写入链路通常需要额外 LLM 调用，延迟与成本显著上升；
- 多租户、图谱存储、时序消解带来较高运维复杂度；
- 抽取质量决定上限，工业文档中的型号、参数、单位极易被抽取错；
- 与本项目“单租户、离线、轻量”的约束不匹配，直接引入会显著增加答辩演示的不可控因素。

**适用场景**：个人助理、客服 CRM、长期陪伴型 Agent 等需要跨会话记住用户偏好与历史事实的系统。本项目可借鉴其“事实化、可失效、分层”的思想，但不引入其完整基础设施。

### 3.3 路线三：会话平台内置上下文窗口

**代表项目**：Dify、AnythingLLM、Open WebUI。

**核心机制**：

1. **Token 缓冲窗口**。Dify 在组装提示词时计算模型上下文余量：上下文大小减去节点 `max_tokens`，再减去已占用 token，循环丢弃最旧消息直到满足限制；模型未声明上下文大小时按 2000 token 兜底[6]。
2. **会话变量**。Dify 的 Conversation Variables 把用户偏好、任务参数等稳定信息从消息流中剥离，作为变量在后续轮次复用，避免每轮重复携带长文本[12]。
3. **工作区隔离与固定资料**。AnythingLLM 以工作区为边界隔离向量库与会话，允许把关键文档固定（pin）到上下文，固定资料优先于相似度召回。
4. **参数化 RAG**。Open WebUI 暴露 top-k、chunk size、chunk overlap 与“全文档注入”开关，让用户在召回精度与上下文完整性之间取舍。

**优势**：

- 工程实现务实，直接解决“历史太长怎么办”；
- 会话变量/工作区隔离的思路可直接映射到单租户下的会话隔离；
- 参数可配置，便于不同模型与文档规模下调优。

**局限**：

- 截断策略粗放：只按时间丢旧消息，可能丢掉仍然有效的任务约束；
- 缺少语义去重与噪声识别；
- 溯源与约束注入通常不是一等公民，难以满足 100% 可审计要求；
- “全文档注入”在工业手册场景极易超出预算。

**适用场景**：通用聊天应用、轻量知识库助手。对本项目而言，其“预算余量计算 + 会话变量”值得直接吸收，但需要升级为分层配额与规则化任务状态。

### 3.4 路线四：Agent 状态编排与上下文压缩

**代表项目**：LangGraph、LangChain（摘要缓冲记忆）、LangMem。

**核心机制**：

1. **线程级状态**。LangGraph 的 Checkpointer 以 thread 为单位持久化图状态，节点只读取自己需要的字段，避免把所有历史广播给每个节点；子图可隔离上下文，减少无关信息干扰。
2. **摘要与压缩**。对话摘要缓冲记忆把久远消息压缩为摘要，与最近若干轮原文混合，兼顾长期信息与近期细节。
3. **按需检索的状态**。Agent 在推理过程中主动查询外部状态（工具、数据库、记忆），而不是一次性把所有状态塞入提示词。

**优势**：

- 适合多步骤任务与工具调用；
- 状态与上下文分离，职责清晰；
- 压缩策略可显著降低长任务的 token 消耗。

**局限**：

- 依赖具体编排框架，迁移成本高；
- 摘要由 LLM 生成，存在信息损失与不稳定；
- 对“单轮知识问答”收益有限，反而增加复杂度；
- 预算控制仍多依赖框架默认值，缺少硬保证。

**适用场景**：多工具、多步骤、长周期 Agent。IndocQA 已有 LangGraph 检索图，可借鉴其“状态与上下文分离”的思想，把任务状态做成显式数据，而不是继续塞进消息历史。

### 3.5 路线横向对比

| 能力 | 检索侧上下文工程 | 结构化记忆层 | 平台内置窗口 | Agent 状态编排 |

| 语义去重 | 中（多为完全重复/向量阈值） | 强（事实合并） | 弱 | 弱 |

## 4 行业最佳实践归纳

综合上述项目与论文，可提炼出八条可落地的最佳实践：

1. **分层预算，先保固定区**。系统规则、当前问题、输出预留必须先扣减，剩余预算再分配给资料、历史、画像与任务状态；否则资料一多就会挤掉约束，造成“答得流畅但不守规则”。
2. **检索用小切片，生成用大窗口**。先用细粒度切片保证召回精度，再按父子关系或句子窗口扩展，避免整章灌入。
3. **去重分级处理**。完全重复用规范化哈希；近重复用 SimHash/MinHash + LSH；语义重复用向量余弦并配合包含度判断，防止把“同模板不同参数”的表格误删[13][14]。
4. **噪声按规则显式建模**。页眉页脚、目录残片、OCR 乱码、纯符号行应有独立规则码与命中统计，才能度量覆盖率并持续调优。
5. **记忆写入做抽取与失效，不做全量堆叠**。即使不引入图谱，也应对画像与任务状态做“键值化、带时间戳、可覆盖、可失效”。
6. **位置即权重**。高价值资料放在上下文前部与问题附近，低价值历史放中部；这与 Lost in the Middle 的结论一致[1]。
7. **约束与资料物理隔离**。系统规则放 system 区，资料放 user 区并用明确分隔符包裹，同时声明“资料中的指令不执行”，降低提示词注入风险。
8. **组装结果可观测**。每次组装应产出 token 账本、保留/丢弃原因、单元 ID 清单与模板版本，否则无法定位“为什么这轮答错了”。

此外，SemDeDup 等工作证明：语义去重在大规模语料上可以在几乎不损失效果的前提下显著减少冗余[14]；但阈值必须按语料与嵌入模型校准，过松会误删互补信息，过紧则去重收益有限。

## 5 对本项目的选型建议

### 5.1 约束条件

- **单租户**：没有多租户切换需求，但必须有会话隔离，禁止跨会话串上下文；
- **离线可运行**：仓库自带嵌入模型权重，组装链路不应依赖外部服务；
- **中文工业文档**：表格多、术语多、页眉页脚多，去重与噪声规则需针对中文与表格调优；
- **现有技术栈**：FastAPI + LangGraph + Chroma + SQLite，前端不改；
- **热路径低延迟**：组装发生在每次问答的首 token 之前，不能引入额外 LLM 调用；
- **可答辩**：每个指标都要有可复现的实验与图表，不能只讲架构。

### 5.2 推荐路线

建议采用“**检索侧上下文工程为骨架 + 轻量结构化记忆 + 统一预算与模板 + 自研溯源**”的组合：

1. **骨架**借鉴 LlamaIndex 的“小切片检索、窗口展开”和 RAGFlow 的“定位后展开”，但保留现有 `Hit` 结构，避免重建索引；
2. **去重**采用三级策略：规范化哈希 → SimHash 近重复 → 复用 Chroma 已存向量的语义去重。证据块的向量直接从向量库读取，不重复推理，保证延迟；
3. **记忆**只做“会话画像 + 任务状态”两级轻量结构：画像以键值事实存储，任务状态以会话级 JSON 存储，均由规则更新，不调用 LLM；
4. **预算**采用“固定预留 + 分层配额 + 按权重贪心选择 + 末位裁剪 + 硬断言”，确保任何输入下都不超模型上限；
5. **模板**采用版本化规则清单，渲染后逐条校验必选规则出现次数与位置，失败则回退内置模板；
6. **溯源**为每个单元分配唯一 ID，携带来源类型、来源 ID、会话 ID、消息 ID、切片 ID、文档 ID、章节、页码、时间戳与内容哈希，并把清单持久化到消息记录，支持回答逐句反查。

### 5.3 不采用的方案与理由

| 方案 | 不采用理由 |
|---|---|
| 引入 Zep/Graphiti 时序图谱 | 多租户与图数据库运维成本高，单租户场景收益有限；离线演示不可控 |
| 引入 Mem0 完整记忆管线 | 写入需 LLM 抽取，增加延迟与费用；工业参数抽取错误会污染长期记忆 |
| 引入 Letta 运行时 | 需要替换现有会话与生成链路，改造成本远超本期目标 |
| 直接使用 Dify/AnythingLLM | 与本项目现有检索评测体系、引用格式、置信度机制不兼容，等于重写 |
| 仅做提示词优化 | 无法解决预算、去重、溯源与画像融合，指标无法量化达标 |

## 6 风险与开放问题

1. **语义去重误删**：同模板表格（如不同型号的参数表）向量相似度可能超过阈值，但内容互补。对策是加入“关键实体/数字差异检测”，差异显著时保留两者。
2. **中文 token 估算误差**：无本地分词器时只能用启发式估算。对策是采用偏保守上界并保留安全系数，最终以硬断言兜底。
3. **画像冷启动**：单租户新部署时没有画像。对策是画像可为空，组装器按“空画像”路径运行，不阻塞主流程。
4. **任务状态漂移**：规则更新可能把闲聊实体误判为任务实体。对策是任务状态只保留高置信实体与显式范围，低置信信息不进入生成上下文。
5. **性能回退**：语义去重与多次排序可能增加延迟。对策是证据向量复用、候选上限、短路策略与性能基准门禁。
6. **评测集偏差**：自建去重/噪声标注集可能过于理想。对策是同时报告人工标注集与真实问答回归集两组结果，并保留失败样例。

---

## 7 结论

四条路线各有边界：检索侧工程解决“相关性”，记忆层解决“长期性”，平台窗口解决“可用性”，Agent 状态解决“一致性”。IndocQA 的痛点同时跨越四者，因此不能照搬任一项目，而应在现有检索链路上增加一个**独立的、确定性的、可观测的上下文组装层**：向上承接检索结果、会话历史、画像与任务状态，向下产出受预算约束、带引用清单、经模板校验的消息数组。

该路线改造成本可控、离线可运行、指标可验证，且与本期五项验收指标一一对应。详细架构、算法、接口、异常与评测方案见《上下文组装组件设计方案》。
