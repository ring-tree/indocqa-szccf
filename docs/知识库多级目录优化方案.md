# 知识库多级目录优化技术方案

- 版本：1.0（2026-11-10）
- 范围：知识库多级目录分类、检索范围限定、存量迁移；同时记录本轮功能性优化的落地结果
- 配套：[待办清单](./待办清单.md)、[系统设计文档](./系统设计文档.md)

## 1. 背景与目标

现状是"单库单集合"：4 份语料、414 个子块全部写入一个 Chroma 集合 `indocqa_<后端>`，文档只按 `doc_id/doc_name` 区分，没有分类维度。带来三个问题：

1. 用户无法按业务域限定检索（例如只在"设备手册"里查故障码，避免行业标准文档干扰）；
2. 文档管理只能平铺，语料增长后不可维护；
3. 无法按目录做权限、统计和增量治理。

目标：在不重建索引、不改变现有检索与入库语义的前提下，引入多级目录，并支持"目录内检索"。

## 2. 开源方案调研与横向对比

调研对象为 GitHub 上活跃的开源知识库/RAG 项目（2026-11 可访问版本）：

| 项目 | 分类模型 | 目录层级 | 检索范围限定 | 迁移/移动成本 | 对本项目的启示 |
|---|---|---|---|---|---|
| [RAGFlow](https://github.com/infiniflow/ragflow) | 文件系统目录 + 知识库；知识库内部不可再建子目录；0.27 新增知识树（Tree） | 文件侧支持嵌套，知识库侧扁平 | 按知识库/文件关联 | 文件移动/重命名，不重新解析 | 目录与知识库解耦；目录是管理维度，不是物理索引 |
| [WeKnora](https://github.com/Tencent/WeKnora) | 知识库内文件夹 + 标签 | 支持多级文件夹，上传目录保留层级 | 文件夹树 + 标签交叉分类 | 移动文件夹只改归类，不重新解析 | 与本项目最接近：一篇文档一个主目录 + 可选标签 |
| [Open WebUI](https://github.com/open-webui/open-webui) | 知识库 + 文件夹 + 标签 | 嵌套目录，支持拖拽 | 知识库/文件夹选择 | 移动文件不重建向量 | 目录树是 UI 主入口，检索范围用选择器 |
| [Dify](https://github.com/langgenius/dify) | Dataset → Document → Chunk 三层 | 无原生嵌套目录 | 按 dataset | 文档移动需换 dataset | 扁平模型简单，但语料多时管理成本高 |
| [AnythingLLM](https://github.com/Mintplex-Labs/anything-llm) | Workspace 隔离 | Workspace 内文档平铺 | 按 workspace | 跨 workspace 需重新嵌入 | 强隔离适合多租户，不适合单库多分类 |

结论：

- 主流做法是**逻辑目录 + 元数据过滤**，而不是"一个目录一个索引"；
- WeKnora 的"移动目录不重新解析"与 RAGFlow 的"目录/知识库解耦"共同说明：目录应作为文档属性，检索时做范围过滤；
- Dify/AnythingLLM 的扁平或强隔离模型都会带来迁移成本，不适合本项目的渐进式演进。

## 3. 架构选型

| 方案 | 做法 | 可行性 | 性能 | 迁移成本 | 结论 |
|---|---|---|---|---|---|
| A. 单集合 + `folder` 元数据过滤 | 目录写入 Chroma metadata 与 manifest，检索按目录子树过滤 | 高，改动集中在 store/searcher | 目录过滤 +10ms（实测） | 仅更新元数据，无重新嵌入 | **采用** |
| B. 每目录一个 Chroma collection | 目录即集合 | 中，需要集合路由与跨目录 fan-out | 跨目录查询需多次检索再融合 | 高，需重建全部向量 | 不采用 |
| C. 每目录独立向量库/服务 | 目录级隔离 | 低，运维复杂 | 单目录快，跨目录慢 | 最高 | 不采用（多租户阶段再考虑） |

选择 A 的关键理由：

1. **零重新嵌入**：目录只是元数据，414 块迁移在启动阶段一次性完成；
2. **跨目录检索不受影响**：不传 `folder` 时行为与原来完全一致；
3. **可扩展**：后续加标签、权限、统计都可复用同一套元数据；
4. **性能可控**：实测目录过滤 p50 从 12.2ms 增至 22.1ms，相对 2.3s 的嵌入耗时不足 0.5%。

## 4. 目录结构设计

### 4.1 路径规范

- 分隔符 `/`，例如 `设备手册/螺杆空压机`；
- 最多 6 级，单级 ≤40 字，总长 ≤200 字；
- 禁止 `..`、控制字符、`<>:"|?*`；反斜杠统一转 `/`；
- 空值：文档默认归入 `未分类`；检索范围空值表示"全部知识库"；
- `未分类` 为系统目录，不可删除，可重命名。

### 4.2 数据模型

manifest（`server/data/chroma/manifest.json`）：

```json
{
  "documents": {
    "doc_id": {
      "filename": "...",
      "chunks": 106,
      "pages": 48,
      "tables": 43,
      "backend": "ollama-bge-m3",
      "folder": "设备手册/螺杆空压机"
    }
  },
  "folders": ["设备手册", "设备手册/螺杆空压机", "行业标准", "行业标准/压缩空气系统"],
  "backend": "ollama-bge-m3"
}
```

Chroma 每个子块的 metadata 增加 `folder`；BM25 侧车不变，目录过滤时通过 `folders_of()` 批量取块的目录。

## 5. 检索设计

1. `ChatRequest.folder` 可选；为空走全库，未知目录直接返回空结果而不是报错；
2. 向量路：`collection.query(where={"folder": {"$in": [子树路径]}})`；
3. 词法路：BM25 先检索，再通过 `store.folders_of()` 批量取目录过滤；
4. 融合、术语扩展、单路补偿、表格加权、多跳逻辑保持不变；
5. `trace` 事件回传 `folder`，前端可解释"本次检索范围"。

## 6. 数据迁移策略

- **触发**：服务启动时 `migrate_folders()` 自动执行，也可手动调用；
- **规则**：按文件名推断初始分类（sourcebook→行业标准/压缩空气系统，螺杆→设备手册/螺杆空压机，无油→设备手册/无油空压机，fixture→评测夹具），未命中归入"未分类"；
- **幂等**：仅处理缺少 `folder` 的文档；已迁移文档不再变更；
- **安全**：后端不一致或集合为空时跳过，避免 manifest 与向量库错位；
- **回滚**：目录只是元数据，回滚只需把 `folder` 改回 `未分类` 或删除 `folders` 字段，不影响向量与 BM25；
- **验证**：迁移后 `GET /api/kb/documents` 每篇文档都有 `folder`，`GET /api/kb/folders` 的 `documentCount` 与文档数一致。

## 7. 功能实现路径

### 7.1 后端接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/kb/folders` | 目录列表（含祖先的文档数/块数） |
| POST | `/api/kb/folders` | 创建目录（自动补齐祖先） |
| PATCH | `/api/kb/folders` | 重命名/移动目录（子树级联） |
| DELETE | `/api/kb/folders?path=&mode=move\|delete` | 删除目录，文档移动到上级或一并删除 |
| POST | `/api/kb/documents/{id}/move` | 移动单篇文档 |
| GET | `/api/kb/documents?folder=` | 按目录子树筛选文档 |
| POST | `/api/kb/ingest` | 新增表单字段 `folder` |
| POST | `/api/chat` | 新增 `folder` 检索范围 |

### 7.2 前端

- 文档管理：左侧目录树（全部/多级缩进/文档数），新建、重命名、删除；上传时目标目录可见；每行文档可下拉移动；
- 问答页：`检索范围` 选择器（全部知识库/具体目录），选择结果持久化到 localStorage，切换文档页后自动刷新目录列表；
- 引用来源：展示目录标签与命中片段，点击引用直接展开原文片段。

## 8. 性能与效果评估

### 8.1 目录过滤开销（414 块，嵌入已缓存）

| 场景 | p50 | max |
|---|---|---|
| 全库检索 | 12.2ms | 13.7ms |
| 目录内检索 | 22.1ms | 24.4ms |
| `folders_of` 批量取 18 个块 | 3.2ms | — |

相对嵌入 2.3s 的占比不足 0.5%，可接受。

### 8.2 40 题评测（优化后，ollama bge-m3）

| 配置 | Recall@5 | Answer 覆盖率 | 多跳跨文档命中 | p50 / p95 |
|---|---|---|---|---|
| 固定参数基线 | 100% | 82% | 91% | 2341 / 2462 ms |
| 自适应（本系统） | 100% | 88% | 91% | 2346 / 2514 ms |
| 消融：去术语扩展 | 100% | 85% | 91% | 2349 / 2460 ms |

对比优化前（同机同索引）：Recall 95%→100%，覆盖率 81%→88%，多跳跨文档 64%→91%。主要来自单路高分补偿、跨语种补偿与表格分数加权。

### 8.3 运行时体验

- 查询嵌入缓存命中后首 token 3.6s→1.1s；
- 寒暄不再检索，总耗时 3.2s→1.3s；
- 目录内问答来源严格收敛到目标子树（设备手册内问 E-05 不再引用评测夹具）。

## 9. 兼容性与稳定性

- 不传 `folder` 时检索、入库、删除、会话、SSE 事件结构与原来一致；
- manifest 新增字段均有默认值，旧 manifest 可直接读取；
- 迁移失败只记录告警，不阻塞服务启动；
- 写目录/移动文档复用 `write_guard` 单写锁；
- 全量单测 58 项通过（原有 48 + 目录新增 9 + 会话 TTL 1）。

## 10. 风险与后续

| 风险 | 现状 | 后续 |
|---|---|---|
| 大规模目录重命名逐文档更新元数据 | 当前 4 文档/414 块，毫秒级 | 文档数上千后改为批量 `collection.update` 或后台任务 |
| 目录过滤依赖 `folder` 元数据完整性 | 启动迁移保证 | 增加一致性巡检接口 |
| 目录数量增长后的选择器体验 | 下拉框可用 | 改为可搜索树形选择器 |
| 未做目录级权限 | 单团队场景 | 与鉴权一起设计 |

其他可选项（见待办清单）：重排 A/B、问答导出、文档详情、检索调试面板、接口鉴权、docx 支持、索引重建入口。
